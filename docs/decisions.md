# 설계 결정과 이유

이 문서는 구현 과정에서 어떤 선택을 했고, 왜 그렇게 풀었는지를 정리한 문서입니다.
코드만 보면 바로 드러나지 않는 의도와 트레이드오프를 함께 남기는 데 초점을 두었습니다.

---

## 1. `course` / `course_seats` 테이블 분리

### 맥락
수강 신청 시 정원 체크와 좌석 차감이 함께 일어나야 하며, 같은 강의에 여러 사용자가 동시에 신청할 때 경합이 발생합니다.
강의 메타 정보(제목, 가격, 상태 등)는 경합과 직접 관련이 없지만, 좌석 카운트는 신청이 발생할 때마다 갱신됩니다.

### 검토한 대안
- **A안 — 단일 `course` 테이블**
  `reservedCount` 컬럼을 `course`에 두고 `@Version`을 `course` 전체에 적용하는 방식입니다.
  장점은 구조가 단순하다는 점입니다.
  단점은 강의 정보 수정과 좌석 변경이 같은 버전을 공유하게 되어 관련 없는 쓰기끼리도 충돌한다는 점입니다. 운영자가 강의 메타 정보를 수정하는 동안 신청 요청까지 함께 영향을 받을 수 있습니다.
- **B안 — `course_seats` 분리 + `@Version`**
  좌석 카운트만 별도 테이블과 엔티티로 분리하고, 낙관 락을 좌석 정보에만 적용하는 방식입니다.
  장점은 충돌 범위를 "좌석 변경"으로 한정할 수 있다는 점입니다. `course` 수정과 수강 신청이 서로 불필요하게 간섭하지 않습니다.
  단점은 강의 생성 시 두 테이블에 함께 INSERT가 필요하고, 좌석 조회 경로도 따로 관리해야 한다는 점입니다.
- **C안 — 좌석 카운트를 `enrollment` 집계로 대체**
  `COUNT(*) WHERE course_id = ? AND status = PENDING/CONFIRMED` 방식으로 매번 집계하는 접근입니다.
  장점은 별도 카운트 컬럼이 없어 정합성 이슈가 줄어든다는 점입니다.
  단점은 신청마다 집계 쿼리와 조건 판단이 필요하고, 경합 상황에서는 결국 DB 락이나 높은 트랜잭션 격리 수준에 의존하게 된다는 점입니다.

### 선택과 이유
**B안**을 선택했습니다.
실제로 경쟁이 붙는 지점은 좌석 카운트이므로, 충돌도 그 지점에만 모이게 하는 편이 자연스럽다고 판단했습니다.
A안은 관련 없는 충돌을 만들고, C안은 읽기 비용과 일관성 보장 비용이 커집니다.

### 감수한 것
- 강의 생성 트랜잭션에서 `course`와 `course_seats` 두 테이블에 함께 INSERT가 필요합니다. 이 부분은 `CourseService.createCourse`에서 처리합니다.
- 좌석 정보를 읽는 경로가 `CourseSeatsRepository.findByCourseId`로 한 번 더 생깁니다.

## 2. 낙관 락 + 재시도(기본 3회) 전략

### 맥락
동시 신청 상황에서는 좌석 카운트 갱신 과정에서 경합이 발생합니다.
정원 초과는 절대 허용할 수 없기 때문에, 경쟁 상황에서도 일관된 결과가 나와야 합니다.

### 검토한 대안
- **A안 — 비관 락 (`SELECT ... FOR UPDATE`)**
  신청 트랜잭션이 좌석 행을 먼저 선점하고 순차 처리하는 방식입니다.
  장점은 충돌 자체를 막을 수 있다는 점입니다.
  단점은 트랜잭션이 끝날 때까지 행을 잠그므로 처리량이 직렬화되고, 좌석이 충분한 일반 요청까지 영향을 받을 수 있다는 점입니다.
- **B안 — 낙관 락 (`@Version`) + 재시도**
  충돌 시 `OptimisticLockingFailureException`을 잡아 정해진 횟수 안에서 재시도하는 방식입니다.
  장점은 충돌이 드문 상황에서 처리량이 높고, DB 락을 오래 잡지 않는다는 점입니다.
  단점은 재시도 횟수만큼 DB 왕복이 늘어날 수 있고, 경합이 심하면 재시도 소진으로 실패를 돌려줘야 한다는 점입니다.
- **C안 — 조건부 UPDATE (`UPDATE ... WHERE reserved_count < capacity`) + affected rows 검사**
  정원 초과 판정을 DB 조건으로 처리하는 방식입니다.
  장점은 원자적 판정이 가능하다는 점입니다.
  단점은 JPA 엔티티의 상태 전이 메서드를 우회하게 되어, 엔티티가 불변식을 책임지는 현재 구조와 맞지 않는다는 점입니다.

### 선택과 이유
**B안**을 선택했습니다.
이 과제에서 가장 중요한 경합은 "마지막 자리 동시 신청" 같은 국소적인 상황이고, 일반적인 요청 흐름에서는 충돌이 드물다고 보았습니다.
이 전제에서는 낙관 락이 비관 락보다 처리량 측면에서 유리하고, JPA의 `@Version`과도 자연스럽게 맞습니다.
재시도는 `EnrollmentService.enroll`에서 단순한 `repeat` 루프로 처리했고, 재시도 소진 시에는 `ENROLLMENT_CONFLICT`(HTTP 409)를 반환해 사용자가 다시 시도할 수 있도록 했습니다.

### 감수한 것
- 경합이 매우 심한 경우에는 재시도가 모두 소진될 수 있습니다. 이 경우에는 `ENROLLMENT_CONFLICT`를 반환합니다. 이 흐름은 `EnrollmentRetryExhaustionTest`에서 검증합니다.
- 재시도 횟수가 지나치게 많아지면 낙관 락의 장점이 줄어듭니다. 현재는 기본 3회로 두고, `enrollment.retry.max-attempts` 프로퍼티로 조정할 수 있게 했습니다.
- 백오프(`Thread.sleep`)는 넣지 않았습니다. 짧은 경합에서는 즉시 재시도가 더 단순하고 빠르다고 판단했습니다.

### 재시도 정책 상세
- 기본 `max-attempts = 3`입니다. 테스트에서는 `@TestPropertySource`로 조정합니다.
- 재시도 대상 예외는 `OptimisticLockingFailureException` 하나입니다.
- 재시도 대상은 신청(`enroll`)만입니다. 취소(`cancel`)는 낙관 락 충돌 시 1회 시도 후 `ENROLLMENT_CONFLICT`를 반환합니다.

## 3. `EnrollmentService` / `EnrollmentProcessor` / `EnrollmentManager` / `EnrollmentReader` 분해

### 맥락
수강 신청 흐름에는 강의 상태 검증, 좌석 예약과 엔롤먼트 생성, 상태 전이(확정/취소), 조회가 모두 섞여 있습니다.
이 책임을 하나의 서비스에 모으면 트랜잭션 경계가 흐려지고, 재시도 루프를 잘못된 위치에 둘 가능성이 커집니다.

### 검토한 대안
- **A안 — 단일 `EnrollmentService`**
  모든 메서드를 한 클래스에 두고 `@Transactional`을 메서드 단위로 부여하는 방식입니다.
  단점은 재시도 루프를 트랜잭션 바깥에 두기 어려워진다는 점입니다. 같은 클래스 내부 호출에서는 프록시가 우회되기 때문에 의도한 대로 동작하지 않을 수 있습니다.
- **B안 — 책임별 분해**
  조정자(Service), 쓰기(Processor, Manager), 읽기(Reader)로 역할을 나누는 방식입니다.
  Service에는 트랜잭션을 두지 않고, Processor/Manager에만 `@Transactional`을 둡니다.
  재시도 루프는 Service에 두고, 트랜잭션 바깥에서 Processor를 반복 호출합니다.

### 선택과 이유
**B안**을 선택했습니다.
재시도 루프가 트랜잭션 경계 **바깥**에 있어야 한다는 점이 구조를 결정했습니다.
Processor는 "좌석 예약 + 엔롤먼트 저장"을 한 트랜잭션으로 묶고, Service는 그 호출을 재시도로 감쌉니다.
이 경계가 섞이면 재시도가 같은 트랜잭션 안에서 반복되어 의미가 없어집니다.

- `EnrollmentProcessor`는 `enroll`, `cancel`을 담당합니다. 좌석 변경과 엔롤먼트 쓰기가 한 트랜잭션 안에 있습니다.
- `EnrollmentManager`는 `confirm`을 담당합니다. 결제 확정은 좌석 수를 바꾸지 않기 때문에 별도 컴포넌트로 분리했습니다.
- `EnrollmentReader`는 `getEnrollments`를 담당합니다. 읽기 전용 흐름입니다.
- `EnrollmentService`는 파사드 역할을 하며, 강의 상태 검증과 재시도 루프, 예외 변환을 담당합니다.

### 감수한 것
- 클래스 수가 늘어납니다.
- 처음 보는 사람에게는 Service가 트랜잭션 없이 Processor를 호출하는 구조가 낯설 수 있습니다. 그래서 이 의도를 문서로 남겼습니다.

## 4. API URL은 리소스 중심으로 유지

### 맥락
"내 수강 신청 목록 조회"는 `/api/v1/users/me/enrollments` 또는 `/api/v1/me/enrollments` 같은 형태로 설계할 수도 있습니다.

### 검토한 대안
- **A안 — `/me` 접두**
  인증 맥락을 URL에 드러내는 방식입니다.
- **B안 — 리소스 루트 + 호출자 컨텍스트**
  `/api/v1/enrollments`처럼 리소스 중심 URL을 두고, 호출자 정보는 인증 컨텍스트로 판단하는 방식입니다.

### 선택과 이유
**B안**을 선택했습니다.
호출자 컨텍스트는 인증 레이어가 들고 가고, URL은 리소스 의미에 집중하는 편이 더 자연스럽다고 판단했습니다.
그래서 "내 수강 신청 목록"도 `/api/v1/enrollments`로 표현했습니다.
크리에이터 전용 수강생 목록은 `/api/v1/courses/{courseId}/enrollments`처럼 리소스 계층 구조를 따릅니다.

### 감수한 것
- 관리자용 전체 조회처럼 다른 권한 시나리오가 추가되면 권한 정책이 더 명확해져야 합니다. 현재는 과제 범위에 맞춰 단순화했습니다.

## 5. JPA 엔티티와 도메인 `data class` 분리

### 맥락
JPA 엔티티를 서비스와 컨트롤러 경계까지 그대로 사용할지, 별도 도메인 모델을 둘지 결정이 필요했습니다.

### 검토한 대안
- **A안 — 엔티티를 도메인으로 겸용**
  한 클래스가 영속성과 도메인 의미를 모두 담당하는 방식입니다.
  장점은 클래스 수가 줄어든다는 점입니다.
  단점은 프록시나 영속성 컨텍스트 같은 세부사항이 서비스와 API 경계로 새어 나올 수 있다는 점입니다.
- **B안 — `xxxEntity` ↔ `xxx` data class 분리**
  `CourseEntity` / `Course`, `EnrollmentEntity` / `Enrollment`처럼 분리하는 방식입니다.
  Service 레이어에서 Entity를 도메인 모델로 변환하고, 컨트롤러는 도메인 모델만 사용합니다.

### 선택과 이유
**B안**을 선택했습니다.
영속성 세부사항이 서비스 로직이나 응답 모델에 직접 섞이는 것을 피하고 싶었습니다.
도메인 모델은 `data class`로 두어 테스트 작성과 응답 변환도 단순하게 유지했습니다.

### 감수한 것
- 변환 코드가 추가됩니다. 다만 이는 경계를 분명히 하는 비용으로 받아들였습니다.

## 6. 상태 전이를 엔티티 메서드로 캡슐화

### 맥락
강의 상태(`DRAFT` → `OPEN` → `CLOSED`)와 신청 상태(`PENDING` → `CONFIRMED` → `CANCELLED`)는 허용되지 않는 전이가 있어야 합니다.
좌석 예약(`reserve`/`release`) 역시 `0 <= reservedCount <= capacity`라는 불변식을 지켜야 합니다.

### 검토한 대안
- **A안 — 서비스에서 setter 호출**
  `enrollment.status = CONFIRMED`처럼 서비스에서 직접 상태를 바꾸는 방식입니다.
  단점은 전이 규칙이 서비스 여러 곳에 흩어지기 쉽다는 점입니다.
- **B안 — 엔티티 메서드로 전이 캡슐화**
  `course.open()`, `course.close()`, `enrollment.confirm()`, `enrollment.cancel()`, `seats.reserve()`처럼 엔티티 스스로 상태를 바꾸게 하는 방식입니다.
  전이 조건을 엔티티 내부에 모을 수 있습니다.

### 선택과 이유
**B안**을 선택했습니다.
상태 전이 규칙은 엔티티가 스스로 지키는 편이 안전하다고 판단했습니다.
서비스는 "무엇을 할지"에 집중하고, 엔티티는 "이 전이가 가능한지"를 책임지도록 역할을 나눴습니다.

### 감수한 것
- 엔티티 안에 비교적 얕은 수준의 도메인 로직이 들어갑니다. 하지만 이 정도의 책임은 엔티티가 갖는 편이 오히려 자연스럽다고 보았습니다.

## 7. 로컬 DB는 H2 (MySQL 모드) + `ddl-auto=create-drop`

### 맥락
과제에서는 H2, MySQL, PostgreSQL 중 하나를 선택할 수 있습니다.
중요한 조건은 평가자가 별도 설치 없이 바로 실행해 볼 수 있어야 한다는 점이었습니다.

### 검토한 대안
- **A안 — MySQL/PostgreSQL + Docker Compose**
  실제 운영 환경에 더 가까운 방식입니다.
  장점은 프로덕션 유사성이 높다는 점입니다.
  단점은 평가자가 Docker를 실행하거나 DB를 따로 준비해야 한다는 점입니다.
- **B안 — H2 in-memory, MySQL 모드**
  `jdbc:h2:mem:course;MODE=MySQL` 기반으로 실행하는 방식입니다.
  장점은 의존성이 거의 없고, 실행 즉시 스키마를 만들 수 있다는 점입니다.
  단점은 실제 MySQL과 완전히 같지는 않다는 점입니다.

### 선택과 이유
**B안**을 선택했습니다.
제출 후 바로 실행해 볼 수 있어야 한다는 조건에 가장 잘 맞는 방식이었기 때문입니다.
스키마는 `ddl-auto=create-drop`으로 자동 생성하고, 참고용 DDL은 `docs/schema.sql`에 따로 정리했습니다.

### 감수한 것
- MySQL이나 PostgreSQL 특화 기능은 사용하지 않았습니다.
- 테스트도 모두 H2 위에서 수행하므로, 특정 DB에서만 드러나는 차이는 별도로 확인해야 합니다.

## 8. 동시성 증빙은 Awaitility + `Executors` + `CountDownLatch`

### 맥락
여러 사용자가 동시에 마지막 자리에 신청하는 상황을 테스트에서 재현할 수 있어야 했습니다.

### 검토한 대안
- **A안 — JMeter/k6 외부 부하 테스트**
  외부 도구로 부하를 걸어보는 방식입니다.
  단점은 CI에서 자동으로 돌리기 어렵고, 이 과제에서 먼저 증명해야 하는 것은 부하 성능보다 정합성이라는 점입니다.
- **B안 — JVM 내 멀티스레드 + Awaitility**
  `Executors.newFixedThreadPool`, `CountDownLatch`, `Awaitility`를 조합하는 방식입니다.
  장점은 테스트 코드 안에서 재현 가능하고, CI에서도 자동 실행할 수 있다는 점입니다.

### 선택과 이유
**B안**을 선택했습니다.
이 과제에서 먼저 보여줘야 하는 것은 "정원을 초과하지 않는다"는 정합성이었기 때문입니다.
`CountDownLatch`로 스레드를 동시에 출발시키고, `Awaitility`로 결과가 모일 때까지 기다리는 패턴이 가장 단순하고 재현 가능하다고 판단했습니다.

`EnrollmentConcurrencyTest`는 재시도가 충분할 때 정원만큼 정확히 성공하는 것을 보여줍니다.
`EnrollmentRetryExhaustionTest`는 재시도가 부족할 때 `ENROLLMENT_CONFLICT`가 발생할 수 있다는 점을 보여줍니다.

### 감수한 것
- JVM 내부 멀티스레드 테스트이기 때문에, 실제 다중 인스턴스 분산 환경 전체를 그대로 재현하는 것은 아닙니다.
- 재시도 정책에는 백오프를 두지 않았습니다. 현재 범위에서는 단순한 즉시 재시도가 더 적절하다고 판단했습니다.
